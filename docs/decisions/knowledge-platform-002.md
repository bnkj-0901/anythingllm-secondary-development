# ADR-002：以 AnythingLLM 作为知识库通用底座

## 状态

Accepted（首期实施基线）

## 日期

2026-10-15

## 背景

项目需要先交付知识库，后续才考虑 ERP 和 App。完整方案涉及文档解析、图片 OCR、音频转写、向量检索、问答引用、多用户空间和模型适配。如果全部自研，首期会重复实现已经成熟的通用能力，延长可用版本的时间。

## 决策

采用 AnythingLLM v1.18.0 作为首期整合基线，通过 `integrations/anythingllm/` 提供启动和配置入口。先验证原版源码，再对缺失的版本发布、人工确认、审计和微信权限做必要适配，不预设重建一套账号、管理后台或 RAG 引擎。

## 备选方案

### 自研 FastAPI + pgvector

边界最干净，但要从零实现解析、任务、工作空间和引用问答，首期成本与工期明显增加。保留为未来需要强定制时的替换方向。

### MaxKB

功能覆盖较好，官方仓库标注 GPLv3。选择 MIT 的 AnythingLLM 可以简化后续修改与分发时的许可处理；GPLv3 同样允许商业使用，若后续选择 MaxKB，需要按实际修改、组合和分发方式履行其许可义务。

### RAGFlow

解析与检索能力强，Apache-2.0 友好，但官方建议起步配置约 4 CPU、16 GB RAM、50 GB 磁盘，首期本地验证负担较大。后续若复杂 PDF 或表格质量成为瓶颈再评估。

## 后果

- 可以先复用成熟的文档、OCR/音频和 RAG 流程，缩短首期验证时间。
- 上游版本升级、依赖许可证和数据供应商条款必须单独跟踪。
- 底座已有多用户权限先复用并实测；微信接入时需服务端授权映射。底座 developer API key 具有管理能力，不直接下发给用户端。
- 图片识别不能自动形成正式知识，人工确认协议必须在适配层强制执行。
