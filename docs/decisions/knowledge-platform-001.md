# ADR：微信知识库首期架构与知识治理边界

日期：2026-10-15。状态：Proposed（方案建议，非已经部署的事实）。

实施路线更新：决策 2–4 的自研方案由 [ADR-002](knowledge-platform-002.md) 调整为优先复用开源知识库。此处的知识治理、权限和图片人工确认要求继续保留；ERP 和 App 已后置。

关联：[完整技术方案](../微信多模态知识库完整技术方案.md)。

## 背景

需要持续接收语音、图片、文字、文档，在微信查询最新有效知识，且能纠错、追溯、限制公开范围。维护人员和预算有限，当前无可复用业务代码作为既定约束。

## 决策 1：小程序为主，公众号为辅助

小程序承载多模态上传、原件预览、权限和版本；公众号承载轻量消息与入口。原因是公众号通用文件管理不等同于小程序能力，耗时生成不能阻塞五秒回调窗口。

替代方案：仅公众号。优点是入口轻；缺点是管理、长任务、文档录入和引用预览受限。仅 H5 可更快试验，但不作为微信录音/文件能力的默认等价替代。

## 决策 2：模块化单体 API + 独立 Worker

业务权限、发布和查询在同一清晰边界内实现，异步解析独立资源隔离。相比微服务可减少分布式事务和运维成本；未来按实际瓶颈拆分，不预先拆大量服务。

代价是共享发布节奏，需严格模块接口、独立 Worker 镜像和执行限额，防止恶意文件影响查询。

## 决策 3：PostgreSQL 为事实源，pgvector 为首期向量存储

版本、授权、发布快照和任务状态放在事务数据库；中文分词后构建词法索引，再与向量融合。Redis 不是业务事实源，COS 保存原件。

替代方案：独立搜索/向量库。优点是专项检索能力和扩容；缺点是增加授权与版本同步复杂度。用真实 Recall@k、p95 延迟和资源曲线确定迁移，而非固定片段阈值。

## 决策 4：RAG 提供事实，不以微调存放每日知识

事实通过资料版本和引用实时更新，模型通过适配层调用。避免微调周期、知识不可删除/不可追溯和专用 GPU 成本；代价是必须做好解析、召回、重排和拒答。

## 决策 5：反馈形成候选，不直接公开

原始证据、AI 摘要、用户纠错和正式知识分离。公开/团队发布经过审核和评测，私有内容由所有者确认。撤回权限从检索、缓存、会话和原件同步执行。

替代方案：所有聊天自动入库。可减少操作，但混淆问题、猜测与事实，容易形成错误自我强化，因此不采用。

## 决策 6：知识与记账图片识别必须人工确认

用户已明确要求两种用途均支持图片识别完人工确认。OCR/视觉输出只生成待确认草稿，原图与识别值可对照编辑；知识点击确认后按空间规则保存/送审，记账点击“确认入账”后在业务事务中校验和登记。保存草稿、取消、拒绝、识别失败均不产生正式知识索引或业务流水。

后端将人工最终值与草稿版本、原图及确认人绑定；重新识别或修改后旧确认失效。发布/过账接口验证快照和权限并防重复提交，不能依赖高识别置信度或前端按钮代替确认。这样防止错识别金额、数量和日期直接污染知识或账目。

## 后果与复核条件

先交付一条真实文字闭环，再增加媒体与公众号；采购前验证云数据库 pgvector 扩展、微信账号接口资格、模型数据地域与供应商条款。公开范围、流量或强合规需求改变时更新该记录，旧记录保留并由新 ADR 替代。
