# ADR-003：在 AnythingLLM 源码内完成知识库业务二次开发

## 状态与日期

Accepted（架构方向已由用户明确选择，迁移尚未实施）。2026-10-19。

替代 [ADR-002](knowledge-platform-002.md) 中通过外部适配与运行时补充业务的实施方式；继续采用 AnythingLLM、保留 MIT、ERP/App 后置。此前 ADR 和验证记录保留历史含义。

## 背景

原版 v1.18.0 提供工作空间权限和单空间 RAG，不能直接提供“普通用户共享投稿→管理员审核→共享＋本人私有联合检索”。已有本地功能靠启动预加载、函数替换、页面注入和 `system_settings` 中的业务 JSON 实现，且仍缺上述完整流程。用户明确要求停止这条扩展路线，直接进行源码二次开发。

## 决策

1. 以当前 AnythingLLM 源码建立可版本管理的项目开发分支。前端页面、服务端路由、模型、检索与必要 Collector 兼容直接修改源码；沿用原有解析、embedding、向量适配和引用能力。
2. 一个产品、一套账号和业务数据库。知识业务是现有 server 内的模块；Collector 保留原有进程职责。首期继续用 SQLite/Prisma 与现有向量配置。
3. 正式数据模型记录所属、资料版本、图片资产、审核事件和索引任务；`system_settings` 回归配置用途。使用增量迁移保留账号和数据。
4. 普通用户可管理本人私有资料和提交共享资料。图片人工核对与共享管理员审核分别实施；只有授权发布且成功索引的版本能被检索。
5. 所有启用的知识检索入口共用服务端授权的联合检索。用户默认查共享＋本人私有，管理员管理权不自动扩大其日常问答范围。
6. 迁移完成后的正常启动不使用预加载补丁、动态方法替换、页面脚本注入，不新增调用本机 developer API 的上层业务服务。

详细范围、数据约束与验收见 [源码开发规格](../specs/anythingllm-source-development.md)。

## 取舍

运行时适配对原版文件改动少，但依赖内部函数、加载顺序及注入页面，业务与版本治理分散，因此停止作为目标架构。独立上层服务能够隔离修改，但会增加身份桥接及业务/检索调用边界，用户已排除。直接源码开发使业务和权限在同一应用中可追溯，代价是需要维护项目分支并审核合并上游变更。

共享/私有仅描述内容可见性，不建立租户、企业组织或 SaaS 计费体系。独立 App 与 ERP 继续后置，微信 H5 保留同一应用入口。

## 迁移约束与后果

- 旧功能可以迁移复用实现思路和有意义测试，不能把运行时注入改成另一个加载器后称为完成源码开发。
- 先备份、在副本演练并核对所属与原件；未知旧空间不自动公开，共享历史资料需管理员确认发布清单。
- 数据库为发布/撤回事实源，向量是可恢复的检索副本。先索引后激活，先停用后清理；统一检索在进入模型前过滤有效版本。
- 版本管理已调整为：`main` 首个提交保存原版源码树；开发分支的第二个提交保留当前目录布局，将源码作为普通文件放入 `vendor/anythingllm/` 并保存现有扩展。未来上游更新按差异合并，不能覆盖本地开发。
- `fetch-source.ps1` 已兼容项目仓库内跟踪的源码，旧本地嵌套检出仍要求与锁定原版一致；正式开发后的启动切换和迁移验证仍需完成。
- 文档梳理不等同于代码切换；本次不迁移数据库、不停止服务、不删除旧实现。

## 验证

以 [任务清单](../../tasks/todo.md) 为交付检查项。核心门槛：A 能在一次问答引用共享与 A 私有，不能读取 B 私有、待审/驳回/失败/撤回共享；所有启用入口一致；无预加载运行；旧数据迁移与备份恢复可验证。
